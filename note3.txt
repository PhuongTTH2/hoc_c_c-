PHẦN 1: TỔNG QUAN DỰ ÁN
1.1. Mục tiêu dự án
Xây dựng một Web Tool cho phép tự động hóa việc tạo và đồng bộ dữ liệu giữa 4 hệ thống doanh nghiệp:
STT	Hệ thống	Chức năng tự động hóa
1	Jira	Tạo Task/Issue, cập nhật thông tin, đồng bộ task về dashboard
2	Git (GitHub/GitLab)	Tạo branch mới từ main/master, tạo commit đầu tiên
3	SharePoint	Tạo folder theo cấu trúc, copy template vào folder
4	Confluence	Tạo page mới từ template, cập nhật nội dung
1.2. Yêu cầu chức năng
STT	Yêu cầu	Mô tả chi tiết
1	Dashboard	Hiển thị tất cả task từ Jira với đầy đủ: tên task, người tạo, ngày bắt đầu, ngày kết thúc, mức độ ưu tiên
2	CRUD Task	Tạo mới, chỉnh sửa, xóa task (process execution)
3	Tự động hóa 4 hệ thống	Một click gửi API đến Jira, Git, SharePoint, Confluence đồng thời
4	Theo dõi lịch sử	Xem chi tiết từng lần thực thi, log lỗi, thời gian xử lý
5	Đồng bộ Jira	Tự động đồng bộ task từ Jira về hệ thống, hiển thị real-time
1.3. Yêu cầu phi chức năng
STT	Yêu cầu	Mô tả
1	Hiệu năng	Thời gian xử lý mỗi task không quá 30 giây
2	Độ sẵn sàng	Hệ thống hoạt động 99.9% thời gian
3	Bảo mật	Mã hóa token, phân quyền người dùng (RBAC)
4	Nhất quán dữ liệu	Đảm bảo All-or-Nothing: thành công cả 4 hệ thống hoặc không hệ thống nào
5	Khả năng mở rộng	Dễ dàng thêm integration mới (Slack, Teams, etc.)

Service	Chức năng	Tương tự trong thực tế

Integration Service	Điều phối gọi 4 hệ thống, quản lý transaction	Bộ phận điều phối công việc
Jira Service	Giao tiếp với Jira API	Chuyên viên liên hệ với Jira

Confluence Service	Giao tiếp với Confluence API	Chuyên viên liên hệ với Confluence

Notification Service	Gửi thông báo qua email/web	Bộ phận chăm sóc khách hàng
Lợi ích của Microservices:
•	✅ Cách ly lỗi: Jira bị lỗi chỉ ảnh hưởng Jira Service, các service khác vẫn hoạt động
•	✅ Mở rộng linh hoạt: Giờ cao điểm chỉ tăng instance cho service đang quá tải
•	✅ Bảo trì dễ dàng: Sửa một service không cần restart toàn hệ thống

2.4. Cập nhật thời gian thực (Real-time Updates)
Vấn đề: HTTP Polling (hỏi liên tục) tốn tài nguyên, độ trễ cao.
Giải pháp: WebSocket - kết nối hai chiều, đẩy dữ liệu ngay khi có cập nhật.
Phương thức	Cách hoạt động	Độ trễ	Tài nguyên
HTTP Polling	Mỗi 5 giây hỏi "có tin mới không?"	5 giây	Cao
WebSocket	Mở kết nối, server đẩy tin ngay	< 1 giây	Thấp

PHẦN 4: TRANSACTION & CALLBACK COMPENSATION
(Xử lý lỗi - Rollback không lưu dữ liệu)
4.1. Vấn đề cần giải quyết
Khi người dùng click "Execute" để tạo task trên 4 hệ thống cùng lúc, có thể xảy ra tình huống:
text
VÍ DỤ VỀ SỰ CỐ:
┌─────────────────────────────────────────────────────────────────────────────┐
│ Bước 1: Gọi Jira API     → ✅ Thành công (Đã tạo ticket PROJ-123)          │
│ Bước 2: Gọi Git API      → ✅ Thành công (Đã tạo branch feature/PROJ-123)  │
│ Bước 3: Gọi SharePoint   → ❌ THẤT BẠI (Lỗi mạng, không tạo được folder)   │
│ Bước 4: Gọi Confluence   → ⏸ Chưa chạy                                    │
└─────────────────────────────────────────────────────────────────────────────┘

HẬU QUẢ:
- Jira đã có ticket mới nhưng không có folder SharePoint tương ứng
- Git đã có branch mới nhưng không có tài liệu trên Confluence
- Dữ liệu không nhất quán giữa 4 hệ thống
- Người dùng phải tự tay xóa ticket Jira, xóa branch Git
Yêu cầu: Phải đảm bảo Tất cả hoặc Không gì cả (All or Nothing):
•	Nếu thành công: Cả 4 hệ thống đều có dữ liệu + Database được lưu
•	Nếu thất bại: Không hệ thống nào có dữ liệu mới + Database không lưu gì
4.2. Giải pháp: Transaction với Compensation Callback
Khái niệm:
•	Transaction ở đây KHÔNG PHẢI là transaction trong SQL, mà là transaction ở tầng ứng dụng - một đơn vị công việc bao gồm nhiều API call đến các hệ thống khác nhau
•	Compensation Callback là cơ chế "rollback" cho các API call: khi gọi API tạo dữ liệu (CREATE), ta đồng thời chuẩn bị sẵn một API hủy dữ liệu (DELETE)
4.3. Sơ đồ Transaction Manager
text
┌─────────────────────────────────────────────────────────────────────────────┐
│                    TRANSACTION MANAGER (Python Backend)                     │
│                                                                             │
│  ┌───────────────────────────────────────────────────────────────────────┐ │
│  │                    COMPENSATION STACK                                 │ │
│  │  (Danh sách các callback đã chuẩn bị để rollback)                    │ │
│  │  ┌─────────────────────────────────────────────────────────────────┐ │ │
│  │  │ [1] Jira Compensation:  DELETE /issue/PROJ-123                 │ │ │
│  │  │ [2] Git Compensation:   DELETE /branch/feature/PROJ-123        │ │ │
│  │  │ [3] SharePoint Comp:    DELETE /folder/PROJ-123                │ │ │
│  │  │ [4] Confluence Comp:    DELETE /page/123456                    │ │ │
│  │  └─────────────────────────────────────────────────────────────────┘ │ │
│  └───────────────────────────────────────────────────────────────────────┘ │
│                                                                             │
│  CƠ CHẾ:                                                                   │
│  - Mỗi khi gọi API thành công → Push callback vào stack                    │
│  - Nếu bất kỳ bước thất bại → Pop stack và gọi callback theo thứ tự ngược │

4.6. Code Python minh họa (Transaction Manager)
python
class TransactionManager:
    """Quản lý transaction với compensation callback"""
    
    def __init__(self):
        self.compensation_stack = []  # Stack lưu các callback
        self.results = {}              # Lưu kết quả tạm thời
    
    def execute_with_transaction(self, steps):
        """
        Thực thi các bước trong transaction
        steps: list of (action, compensation) tuples
        """
        try:
            # Thực hiện từng bước
            for i, (action, compensation) in enumerate(steps):
                try:
                    # Gọi action (ví dụ: tạo Jira ticket)
                    result = action()
                    self.results[f"step_{i}"] = result
                    # Push compensation vào stack
                    self.compensation_stack.append(compensation)
                    
                except Exception as e:
                    # Có lỗi → rollback
                    print(f"Step {i} failed: {e}")
                    self._rollback()
                    raise Exception(f"Transaction failed at step {i}: {e}")
            
            # Tất cả thành công → commit
            self._commit()
            return {"status": "success", "results": self.results}
            
        except Exception as e:
            return {"status": "failed", "error": str(e)}
    
    def _rollback(self):
        """Gọi tất cả compensation callback theo thứ tự ngược"""
        print(f"Rolling back {len(self.compensation_stack)} operations...")
        
        while self.compensation_stack:
            compensation = self.compensation_stack.pop()
            try:
                compensation()  # Gọi API xóa dữ liệu
                print(f"Compensation successful")
            except Exception as e:
                print(f"Compensation failed: {e}")
                # Log lỗi nhưng vẫn tiếp tục rollback các bước khác
    
    def _commit(self):
        """Commit transaction - lưu vào database"""
        print("Committing transaction...")
        # Lưu dữ liệu vào database
        # INSERT vào 4 bảng
        print("Database committed")
        # Xóa stack
        self.compensation_stack.clear()
4.7. Tóm tắt cơ chế
Thành phần	Mô tả
Transaction Manager	Quản lý toàn bộ quá trình, lưu stack compensation
Action	Hàm gọi API tạo dữ liệu (CREATE)
Compensation	Hàm gọi API xóa dữ liệu (DELETE)
Stack	Lưu các compensation theo thứ tự thực hiện
Rollback	Gọi compensation theo thứ tự ngược khi có lỗi
Commit	Lưu database khi tất cả thành công
